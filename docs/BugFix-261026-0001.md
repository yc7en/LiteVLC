# BugFix-261026-0001 macOS 打包 hdiutil 偶发失败导致 dmg 缺失

## 一、缺陷描述

打 `v1.1.5` tag 触发发布流水线后：

- Windows `Build x64`：success
- macOS `Build x64`：success
- macOS `Build arm64`：**failure**，失败步骤「塞入 VLC + 修路径 + ad-hoc 签名」

同一个 commit（`1236800`）在 4 分钟前的 main 推送运行里三条腿全绿，说明不是代码问题，是打包环节的偶发失败。

Release 结果印证了影响面：`v1.1.5` 只有 3 个资产（`macos-x64.dmg` / `Setup.exe` / `win64.zip`），**缺 `macos-arm64.dmg`** —— 而 arm64 恰恰是 Mac 用户的主流架构。

注解里 `ERR` trap 已经把真实位置递出来了：

```
!! 中止: 第 139 行, 命令 [hdiutil create -volname "LiteVlcPlayer 1.1.5"
   -srcfolder ".../dmg-stage" -ov -format UDZO "...arm64.dmg" > /dev/null], 退出码 1
```

`hdiutil` 在 CI runner 上失败的常见原因：临时挂载点被上一轮残留占住（Resource busy）、
`/Volumes` 挂载未及时释放、磁盘暂存空间不足。这类问题**重试一次基本就能过**，
但原脚本是「一次失败 = 整条流水线失败」，代价过大。

另有一处诊断缺陷：`hdiutil ... >/dev/null` 只吞了 stdout，stderr 里的真实报错
（如 `hdiutil: create failed - Resource busy`）没有被 CI 的错误汇总正则匹配到，
所以注解里只看到「退出码 1」，看不到 hdiutil 自己说了什么。

## 二、修复方法与实现

`packaging/macos/bundle.sh` 第 5 步（生成 dmg）改为：

1. **重试 3 次**，每次先 `rm -f "$DMG"` 清掉半成品，失败后 `sleep 5` 再试；
2. 每次失败往 stderr 打一行 `!! hdiutil 第 N 次失败`，保留在 CI 日志里；
3. 三次都失败才 `exit 1`，并额外输出 `df -h "$OUT_DIR"`，便于判断是不是磁盘空间问题；
4. 成功后才清理 `dmg-stage`（原实现失败时会留下 stage 目录，重试时被 `rm -rf` 覆盖，这里保持一致）。

用 `if hdiutil ...; then` 包住命令，`set -e` 不会在重试分支里提前退出，`ERR` trap 也不会误触发。

## 三、验证

- `bash -n packaging/macos/bundle.sh` 语法通过。
- 用 `E:/tmp/brepro` 的 macOS 工具桩（假 `hdiutil` / `otool` / `codesign` / `lipo` / `PlistBuddy`）完整跑一遍 arm64 流程，退出码 0，dmg 正常产出。
- 待 CI 复跑确认（tag 重建后两条腿都出包）。
