# BugFix-261021-0002：AES 加密源经中继后拿不到有效媒体

## 缺陷描述

开启「过滤 HLS 插播广告」后，部分地址无法播放（如 `https://v.gsuus.com/play/xbo2pBza`），
提示「这一集没能播放（没拿到有效媒体）」。关闭过滤则正常。

### 根因分析

该源与之前验证过的 dytt 源有两个本质区别：

1. **AES-128 加密**：媒体清单头部有 `#EXT-X-KEY:METHOD=AES-128,URI="enc.key"`，密钥是**相对路径**；
2. **没有一条 `EXT-X-DISCONTINUITY`**（广告过滤本不会动它），分片是另一台主机的绝对地址。

问题出在中继链路：清单经 `HlsRelay` 改写后，VLC 拿到的清单地址是
`http://127.0.0.1:<port>/t/<token>`，VLC 按 RFC 8216 把相对的 `enc.key` 解析到
**本地中继**上请求 → 中继只登记了清单 token，不认识 `enc.key` → 404 → 解密失败 →
VLC 报错、拿不到时长，触发连播保护提示。

而 `HlsFilter::processMedia` 的 `absolutize` 只处理了**非 `#` 开头的分片行**，
`#EXT-X-KEY` / `#EXT-X-MAP` 等标签行内嵌的 `URI="..."` 属性原样保留，正是漏点。

### 连带发现的问题

- `HlsFilter::processMaster` 里 `wrapChild` 返回空串（该子清单此前拉取失败、不再走中继）
  时，子清单行会被写成**空行**，主清单直接损坏；
- `HlsRelay::serveToken` 上游拉取失败或返回的不是 m3u8（HTML 风控页）时回 502/错误页，
  VLC 只能直接失败——其实应该 302 回源站让 VLC 直连（VLC 自带 UA/Referer，很多站吃得通）。

## 修复方法与实现

1. **`HlsFilter::processMedia`**：新增 `absolutizeUriAttrs()`，对标签行内嵌的
   `URI="..."` 属性做 `base.resolved()` 绝对化；分片行照旧。头部标签区（KEY 常在
   首个 EXTINF 之前）在 `assemble` 时同样处理。
2. **`HlsFilter::processMaster`**：`wrapChild` 返回空串时回退为子清单绝对地址，
   不再写空行。
3. **`HlsRelay`**：新增 `respondRedirect()`；上游拉取失败、或响应体不是
   `#EXTM3U` 开头（HTML 错误页/风控页）时，302 重定向回源站最终 URL，
   让 VLC 直连取原始内容；条目标记 `failed`，后续 `wrapUrl` 退回直连（原有逻辑）。

## 验证

- 用 gsuus 真实清单（AES 相对密钥）做回归用例：密钥 URI 被绝对化为
  `https://v.gsuus.com/play/hls/xbo2pBza/enc.key`，无相对残留；
- 主清单 wrapChild 为空 → 回退绝对地址，无空行；
- 本地源返回 HTML → 中继 302 → 客户端拿到源站原文；
- dytt 广告过滤用例与真实源站端到端全部无回归；
- 测试台 `E:/tmp/hlstest`：35 项断言全部通过。
