# R-261022-0010 macOS 打包脚本架构自检改写与 CI 报错可定位化

## 一、变更背景与原因

`R-261022-0009` 给 `packaging/macos/bundle.sh` 加了第 4 个参数 `ARCH`，并在脚本第 3 段做架构自检。之后：

- 本地（Git Bash / bash 5.3）用桩程序（`otool` / `install_name_tool` / `lipo` / `codesign` / `hdiutil` / `PlistBuddy`）把整个脚本跑完，arm64 路径退出码 0，x64 路径按预期拦截错架构二进制 —— 逻辑本身没问题。
- GitHub 上 `Build arm64` 与 `Build x64` 两条腿**都**失败在同一处：

  ```
  ==> 修插件依赖（逐个加 rpath）
      插件数: 339            # x64 腿是 345
  packaging/macos/bundle.sh: line 82: EXPECT_ARCH
  ```

  第 82 行当时是 `echo "==> 架构自检（$EXPECT_ARCH）"`，而 `EXPECT_ARCH` 在**第 26 行**就已 `EXPECT_ARCH="$ARCH"` 赋值；日志里第 33~79 行的输出齐全，说明赋值那一行确实执行过。报错尾巴还缺了 `: unbound variable` 和行尾换行，属于被截断的不完整信息。

结论：在 macOS runner 自带的 `/bin/bash`（3.2.57）上，第 26 行设置的变量在第 82 行读不到（本地 bash 5.x 无法复现，疑与 bash 3.2 的跨段状态/进程替换交互有关）。既然根因无法在本地确认，就不能再让「自检」依赖 60 行之前的赋值 —— 这属于**可消除的脆弱点**，代价只是把架构推导搬近使用点。

## 二、变更具体内容

### 1. `packaging/macos/bundle.sh`

- **删掉**第 26~27 行的 `EXPECT_ARCH="$ARCH"` 与 `x64 → x86_64` 归一，避免「先赋值、很久以后才用」的跨段依赖。
- **第 3 段（架构自检）就地由 `ARCH` 推导期望架构**，改名为 `ARCH_EXPECTED`（与旧名彻底脱钩，避免任何残留引用）：

  ```bash
  case "${ARCH:-arm64}" in
      x64|x86_64) ARCH_EXPECTED="x86_64" ;;
      arm64)      ARCH_EXPECTED="arm64"  ;;
      *)          ARCH_EXPECTED="${ARCH}" ;;
  esac
  echo "==> 架构自检: 期望 $ARCH_EXPECTED"
  ```

  这样自检结果只取决于命令行第 4 个参数，不依赖脚本前段任何状态。
- **加 `ERR` trap**，失败时把「行号 + 实际命令 + 退出码」打到 stderr：

  ```bash
  trap 'rc=$?; echo "!! 中止: 第 $LINENO 行, 命令 [$BASH_COMMAND], 退出码 $rc" >&2' ERR
  ```

- 启动横幅多打一行 `==> 架构: $ARCH (bash $BASH_VERSION)`，一眼能看出 CI 端 bash 版本与实参。

### 2. `.github/workflows/macos.yml`

- 调用方式改为 `bash -x` 并 `export PS4='+[$LINENO] '`：日志里每条命令都带源文件行号，失败前执行了什么一目了然（临时措施，稳定后可去掉 `-x`）。
- 「打包失败汇总」步骤重写，信息优先级反转 —— 以前把日志**尾巴**塞进注解，尾巴被截断就什么都没了；现在：
  1. 打印 `bash --version`、环境里是否已有 `ARCH` / `EXPECT_ARCH`（排除被父环境污染）；
  2. 打印 `bundle.sh` 关键的 `19~27` / `86~96` 行（确认 CI 上看到的脚本与仓库一致）；
  3. `sed 's/^/  | /' bundle.log` 把**全量日志**写进 step 日志（网页端可翻）；
  4. 注解正文改为**错误行优先**（`grep -nE 'bundle.sh: line|中止:|unbound|command not found|非 (arm64|x86_64)|No such file'`），取不到才退回日志尾巴。
  5. 所有 `$( ... | head ... )` 都补 `|| true`：GitHub 的 run 步骤默认 `-eo pipefail`，`head` 提前关管道会让 `grep` 吃 SIGPIPE，整个赋值语句非零会直接把这一步也搞挂（曾经的隐藏坑）。
