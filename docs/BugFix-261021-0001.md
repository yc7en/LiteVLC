# BugFix-261021-0001 在线片源「能搜到但播放不了」

## 一、缺陷描述

**现象**：在「在线片源」对话框里搜索、选中、双击剧集，窗口标题短暂变化后回到黑屏播放区，画面不动、没有提示、没有报错，控制栏状态也看不出异常。用户只能判断为"播放不了"。

**影响范围**：在线片源（R-261021-0001）功能整体不可用——即使片源正常也可能被误判为故障。

**复现条件**：任意真实 CMS 源；当返回的播放地址属于以下任一情况时必定复现：

- 需要 `Referer` / 特定 UA 的防盗链地址（403）
- 直链已过期或线路已下线（404 / 5xx）
- 返回的是网页（需要网页解析/嗅探的线路）
- 地址里含中文、空格、`&amp;` 或外层引号

## 二、根因分析

用 `E:/tmp/pbtest` 独立调用 `VlcPlayer::openUrl()` 请求公开 HLS 与 mp4，**均能正常起播**，据此排除了播放内核、网络插件（`access/http`、`gnutls`、`adaptive`）与 DLL 部署问题。

真正的缺陷有两层：

1. **`openUrl()` 的返回值具有误导性。** `libvlc_media_player_play()` 只是把请求丢进后台线程就立即返回成功，真正的 403 / 404 / 非法 URI 是数秒后在内核内部失败的。而 `VlcPlayer` 既没有监听 `libvlc_MediaPlayerEncounteredError`，也没有开启日志回调，**失败路径完全静默**。
2. **地址未做清洗。** LibVLC 对未做百分号编码的中文/空格会直接判为非法 URI；`&amp;` 会被当成参数名的一部分导致 403；协议相对地址 `//host/path` 缺少 scheme。这些情况全部表现为"打开成功但永远不出画面"。

## 三、修复方法与实现

### 3.1 新增播放前地址预检 `src/core/StreamProbe.h/.cpp`（326 + 89 行）

**思路**：在把地址交给 LibVLC 之前，先用 `QNetworkAccessManager` 发一次 `GET` + `Range: bytes=0-8191`，用真实响应判断这个地址到底能不能放出画面，并把**实测可用的 UA / Referer** 交给内核。

- 候选请求头**按防盗链常见程度排序**逐组试（`StreamProbe::start`, `candidates` 列表）：

  | 序号 | UA | Referer | 适用场景 |
  |---|---|---|---|
  | 1 | 站点配置的 UA | 站点配置的 Referer | 正常情况 |
  | 2 | 站点配置的 UA | 空 | 站点拒绝错误 Referer（比拒绝"无 Referer"更常见） |
  | 3 | 空（LibVLC 默认） | 空 | 完全裸请求 |
  | 4 | 站点配置的 UA | 媒体地址自身的 origin | 只校验 Referer 域名与媒体同源的站点 |

  重复组合自动去重；`Range` 让服务端只回前 8KB（`kProbeBodyCap`），拿到足够判断的头部即主动 `abort()`（`m_cappedByUs`），不会把整个视频拉下来。

- 判定规则（`StreamProbe::evaluate`）：`#EXTM3U` 开头 / 媒体类 Content-Type（`mpegurl`、`video/`、`audio/`、`octet-stream`、空）/ 媒体后缀（m3u8、mp4、flv、mkv、ts）→ **通过**；HTML 特征 → 「该地址返回的是网页」；其余按状态码翻成人话（403 / 404 / 5xx / 超时 / DNS 失败 / 空响应）。
- 非 `http(s)` 协议（rtmp / rtsp / ftp / magnet）**直接放行**，不参与 HTTP 预检。
- 超时预算：单组 4s（`kProbeTimeoutMs`），整体 12s（`kProbeTotalBudgetMs`，`m_deadline`），避免四组串行超时把用户晾在那里。
- 地址清洗 `sanitizeMediaUrl()`：去 `\r\n\t` 与首尾空白 → 解 `&amp;` → 剥外层引号（JSON 二次序列化常见）→ `//` 补 `http:` → `QUrl::FullyEncoded` 编码中文/空格。`openUrl()` 内部也会再调一次，任何入口都受保护。

### 3.2 `VlcPlayer` 打开错误通道

- `libvlc_log_set()` 注册 `VlcPlayer::vlcLogCallback`，只收 `>= WARNING` 级别的日志，缓存最近若干条供 `friendlyError()` 归因；起播成功时清空缓存。
- 监听 `libvlc_MediaPlayerEncounteredError` 事件，转成 `errorOccurred(QString)` 信号。
- `friendlyError()` 把内核日志关键词映射为可读原因：403 / 404 / 5xx、`connection refused`、`timed out`、`Invalid URL`、`no suitable demux`、`cannot open` 等。

### 3.3 `MainWindow` 接入预检、自动重试与显式报错

- `playOnlineEpisode()` 不再直接 `openUrl`，改为先跑 `StreamProbe`，在 `onStreamProbeFinished()` 里用**实测通过的 header** 起播。
- **自动重试**（`onPlayerError`）：内核报错后换一组请求头重试，最多 2 次（先去掉 Referer，再完全裸请求），覆盖"主清单能过、分片被挡"这一类。重试时若没有实测 header 可用，回退到站点配置的 UA/Referer（`m_lastProbeHasHeaders` 标记来源，避免把空 UA 当有效值）。
- **失败必可见**：手动点击播放失败弹 `QMessageBox::warning`（标题「播放失败」，含原因、剧集名与地址）；自动连播失败只走 OSD，避免连续弹窗刷屏。
- **安全阀**：预检若失败在 TLS 证书或超时上，**不拦播放**，仍交给 LibVLC 再试一次——Qt 在 Windows 走 Schannel、VLC 走 GnuTLS，两者结论可能不同，不能因为 Qt 拒了就判死刑。

## 六、已知边界

- 源站要求「站点首页 Referer 且与媒体不同域」时预检猜不到，只能在源配置的 `referer` 字段手填。
- 需要网页解析 / 嗅探 / JS 执行的线路仍然不支持，只会明确报错，不再静默。
- 分片级防盗链（主清单能过、`.ts` 分片被挡）只能靠重试撞对 header，彻底解决需要本地 127.0.0.1 中继。
