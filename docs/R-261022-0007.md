# R-261022-0007：打 tag 自动发 Release

## 变更背景与原因

1. 双端 CI（R-261022-0005）跑完后，产物只在 Actions → Artifacts 里，**保留 14 天**就过期，
   而且必须登录网页才能下载。
2. `UpdateService` 用的更新源是 GitHub Releases（R-261022-0003），
   所以发布流程必须把安装包放进 Release 的 assets，否则更新功能没有可读取的附件。
3. 手工做法是「下载 artifact → 建 Release → 传两个文件」，每次发版重复一遍，
   容易漏传或传错版本。

## 变更具体内容

1. **两个工作流都增加 tag 触发**：`on.push` 里加 `tags: ['v*']`。
   - GitHub 对 **tag push 不评估 `paths` 过滤**，所以打 tag 一定能触发，
     不会因为“这次没改代码”而漏跑。
2. **增加 `permissions: contents: write`**：`GITHUB_TOKEN` 默认只读，建 Release 需要写权限。
3. **末尾加「发布到 GitHub Release」步骤**，条件 `startsWith(github.ref, 'refs/tags/v')`：
   - 用 `softprops/action-gh-release@v2`，`files:` 指向本端产物；
   - `generate_release_notes: true`，自动带出本次 tag 之前的提交列表；
   - 两个工作流各自把本端文件挂到**同一个 tag 的 Release** 上（动作会复用已存在的 Release），
     所以一次 `git push origin v1.1.3` 就能得到一份带 3 个附件的 Release。
4. **发版清单（版本号四处同步）**：`CMakeLists.txt` 的 `project(... VERSION)`、
   `resources/app.rc` 的 `FILEVERSION`、`installer.iss` 的 `#define MyAppVersion`、
   `package.bat` 的 `APPVER`。CI 里 Setup 版本号从 `CMakeLists.txt` 读取，
   tag 名要与之一致，`UpdateService` 才是按 `tag_name` 去掉 `v` 与当前版本比较。

## 产物命名（与 `UpdateService::platformTag()` 对齐）

| 平台 | 文件名 | platformTag |
|---|---|---|
| Windows | `LiteVlcPlayer-<ver>-Setup.exe` | `win-x64` |
| Windows（便携） | `LiteVlcPlayer-<ver>-win64.zip` | —— |
| macOS | `LiteVlcPlayer-<ver>-arm64.dmg` | `macos-arm64` |

## 只想验证编译、不想发版时

- 推普通提交到 `main`（触发条件仍受 `paths` 限制）；
- 或 Actions 页面手动 `workflow_dispatch`。

两种情况都只上传 Artifacts，不会建 Release。
