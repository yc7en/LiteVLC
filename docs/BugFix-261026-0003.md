# BugFix-261026-0003 订阅地址打不开：配置被塞进图片，且 JSON 带注释

## 一、缺陷描述

用户反馈订阅地址 `http://www.饭太硬.net/tv` 打不开（导入失败），提示 JSON 解析错误。

## 二、原因分析

### 2.1 地址本身是中文域名，但这不是问题

`www.饭太硬.net` 的 Punycode 是 `www.xn--sss604efuw.net`，Qt 的 `QUrl` 能正常处理，
解析与请求都没有障碍（实测最终地址 `http://www.饭太硬.net/tv`，HTTP 200）。

### 2.2 真正的形态：JPEG 图片尾部拼接 base64

用客户端 UA（`okhttp/3.12.1`）请求，服务端返回的不是 JSON、也不是 HTML：

```
HTTP/1.1 200 OK
Content-Type: image/x-ms-bmp          ← 注意：声明成 bmp，实际是 JPEG
Content-Length: 20063
Server: cloudflare

文件结构：
  offset     0 ..  2411   JPEG 图像数据（FFD8FFE0 / JFIF，100x100 缩略图）
  offset  2411 .. 20063   base64 文本（17652 字节，解码后 13238 字节 JSON）
```

这是分发站规避文本检测的常见做法：把配置当「图片」放在图床上，只有按客户端 UA
请求、再把尾部 base64 解出来，才能拿到真正的配置。

### 2.3 配置内部还有 `//` 行注释

解出来的 JSON 第 13、25 行是 `//{"key":"原创",...}` 这种**整行注释**——TVBox 里
停用一个源就是把它注释掉。标准 JSON 不允许注释，`QJsonDocument::fromJson` 会
直接在注释处报 `illegal value`。

两个障碍叠加，所以旧代码无论怎么努力都只能得到一句「JSON 解析失败」。

### 2.4 这份配置本身只有直播源可用

```
sites: 49 条，全部 type=3（csp_*Guard 脚本爬虫，需要 spider.jar 运行时）
lives:  6 条
  · 综合直播     http://193.123.86.190:14888/TV/iptv.php            可用（188 频道）
  · Kimentanm    https://ghproxy.net/.../Kimentanm/aptv/.../iptv.m3u 可用（120 频道）
  · 虎牙一起看   https://sub.ottiptv.cc/huyayqk.m3u                  可用（1007 频道）
  · 斗鱼一起看   https://sub.ottiptv.cc/douyuyqk.m3u                 可用（934 频道）
  · YY轮播       https://sub.ottiptv.cc/yylunbo.m3u                  可用（518 频道）
  · 牛播一       http://127.0.0.1:9978/proxy?do=cctva                不可用（本地代理）
```

即：**修好解析后仍然没有点播源**（49 个全是 type=3），只有 5 个直播源。

## 三、修复方法与实现

全部集中在 `src/core/SourceManager.cpp` 的 `parseConfigJson()`，改成按代价从低到高
逐级尝试，每一级都要求结果「看起来像配置」才认：

```
1. 响应体本身是 JSON（原样 → 剥 // 注释 → 剥 /* */ 注释，自动去 UTF-8 BOM）
2. 整份响应体是 base64
3. 响应体里夹着一段 base64（图片在前、配置在后，扫描 >=256 字节的连续 base64 段）
```

### 3.1 新增 `stripJsonComments()`

逐字节扫描并跟踪字符串状态，只在**字符串外部**剥注释：

- `//` 到行尾（保留换行，避免把下一行拼上来）
- `/* ... */` 块注释
- 字符串内的 `//` 原样保留 —— 否则 `"api": "http://..."` 会被从 `//` 处吃掉

这条容易写错，测试里专门加了断言（`字符串里的 // 未被当成注释`）。

### 3.2 新增 `extractBase64Runs()`

按「连续 base64 字符」切段，只取长度 >= 256 的段。逐个解码后尝试解析，
第一个能解出配置的段即命中。这样即使图片数据里混着随机 ASCII，也不会误判。

### 3.3 新增 `looksLikeConfig()` 作为识别闸门

解码出来的必须是「非空数组」或「含 `sites` / `lives` 数组的对象」才算数。
避免把二进制里偶然解出的 JSON 当配置（测试里用 3 KB 的 `AAAA...` 验证不误判）。

### 3.4 跳过 TVBox 内置本地代理

`http://127.0.0.1:9978/proxy?do=xxx` 是 TVBox 客户端自己起的代理，桌面端没有这个服务。
导入阶段直接跳过，否则用户会看到一个永远「连接被拒绝」的源。

判据收紧为「本机地址 **且** 路径含 `proxy`」，不误伤用户自建在本机的清单服务
（测试台用的 `127.0.0.1:18090/live.txt` 仍然正常导入）。

### 3.5 导入提示说清「为什么没有点播源」

`SourceDialog::importPayload()` 里，当配置有 `sites` 数组却一条都没收进来时，
额外补一行说明：这份配置有 N 个点播站、但没有一个是 type=0/1 的苹果 CMS 接口，
在线搜索页暂时搜不到片，直播源不受影响。

同时把 `livesSkipped` 的措辞从「脚本型直播源」改为「不可用直播源（只有脚本 api，
或指向本机代理地址）」，因为它现在覆盖两种原因。

## 七、遗留

- 这份配置的 49 个点播站全是 `type=3`（`csp_DouDouGuard` / `csp_T4Guard` 等），
  要支持它们需要内嵌 QuickJS + `spider.jar` 运行时，是独立的大特性，不在本次范围。
- 直播清单里的频道地址失效率较高（实测 `101.35.240.114:88` 返回 404），这是
  这类源的常态，需要在播放失败时靠换源解决，不是解析问题。
